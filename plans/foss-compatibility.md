# FOSS compatibility audit — September 17, 2026

Scope: R12 public extension contracts, saved-report compatibility and installation
checks. These changes follow 0.18.0 and are not yet a PyPI release.

## Findings and corrections

1. `CaseImporter.as_model_fn` consumed saved outputs by call order and silently
   produced empty responses after exhaustion. Reordering or repeating cases
   could grade the wrong response, including under parallel execution. The
   compatibility helper now snapshots case identities, rejects ambiguous direct
   inputs and requires recorded string outputs. It is deprecated. Documentation
   uses explicit `run_on_cases` pairs, preserving imported origin and unknown
   target latency. Repeating saved responses does not measure target variation.
2. Reports had version checks and nested evidence validation, but no packaged
   envelope schema. The reader now uses the existing JSON Schema dependency to
   validate v1/v2 envelopes, field types and finite JSON values. Conflicting
   advertised case outcomes are rejected. Additive fields
   remain accepted; unknown report versions/statuses are rejected. The envelope
   does not authenticate evidence. Existing trial/lock validation still applies.
3. The install-smoke workflow executes imports from the repository root, allowing
   source to shadow the installed wheel. An offline script rejects that condition
   and checks the installed schema resource, base API and migration fixtures.
   Workflow corrections and explicit upstream-integration jobs are committed on
   local branch `foss-compatibility-ci`, commit `2eccb5f`. GitHub rejected that
   branch push because the available token lacks `workflow` scope. The code/docs
   commit `6d99655` is pushed to main. Remote CI improvements remain undelivered;
   do not claim those jobs are running.

## Reuse and extension choices

No plugin registry, dataset engine or environment scheduler was added. Python
evaluators/importers, native Gymnasium factories and native Inspect tasks remain
the extension boundaries. Report validation uses standard JSON Schema 2020-12;
optional integrations use normal Python extras. The historical `all` extra is
documented accurately rather than silently adding every heavy development extra.

The guide documents concurrency, grader warmup limits, skipped/error behavior,
dependency declarations, report migration and exact tested upstream versions.
Private case-aware adapter hooks are not advertised as a stable public protocol.
